# 1. Executive Summary

**Bedtime Surahs & Duas** (ঘুমানোর পূর্বের সূরা ও দোয়া) is a lightweight, single-page, **Progressive Web App (PWA)** that presents 10 short Islamic Surahs and Duas for recitation before sleep.

Each item is displayed in three forms inside a collapsible card:

1. **Arabic** text (right-to-left)
2. **Bengali transliteration** (উচ্চারণ — pronunciation)
3. **Bengali meaning** (অর্থ — translation)

The app is built with **Next.js 15 (App Router)**, **React 19**, **TypeScript**, and **Tailwind CSS 4**. It has **no backend, no database, no accounts, and no tracking** — the content is static, typed data in `lib/cards.ts`.

The most significant engineering work is the **PWA layer** (Phases 1–3 of a PWA rollout):

- A hand-written, framework-free **Service Worker** (`public/sw.js`) providing offline support via precaching and a network-first navigation strategy.
- A **Web App Manifest** generated natively by Next.js (`app/manifest.ts`).
- A **self-hiding install button** (`components/InstallButton.tsx` + `hooks/usePwaInstall.ts`) that only appears when the browser offers a native install prompt.
- An **offline fallback page** (`public/offline.html`).
- **localStorage persistence** for the single-open accordion state (`hooks/useCardStates.ts`).

The app is installable, works fully offline after the first visit, respects accessibility (ARIA, keyboard navigation, `prefers-reduced-motion`), and is optimized for both mobile and desktop reading.

**Key components:**
- 7 UI components (Hero, ReadingList, ReadingCard, ProgressBar, ScrollToTopButton, InstallButton, ServiceWorkerRegistrar)
- 4 custom React hooks (card states, PWA install, scroll progress, scroll to top)
- 2 typed data files (content + types)
- 1 hand-written Service Worker + 1 offline HTML page
- 8 PWA icon/favicon assets

# 4. Architecture

The application follows a **custom lightweight layered architecture** typical of a small Next.js App Router project:

```
Data Layer (lib/cards.ts)  →  State Layer (hooks)  →  Presentation Layer (components)  →  Output (app/page.tsx)
```

It is essentially an **MVC-lite** pattern:

- **Model:** `lib/cards.ts` (typed data) and `lib/types.ts` (the `ReadingItem` contract)
- **Controller/State:** hooks (`useCardStates`, `useScrollProgress`, etc.) manage behavior and browser state
- **View:** components render the data and UI

On top of this, a **PWA "additive" layer** wraps the app without changing how it renders:

```
Server (Next.js SSR)
    ↓ HTML
Browser (hydration)
    ↓
Service Worker (public/sw.js) — intercepts fetches, serves offline
    ↓
PWA install path (manifest + InstallButton + usePwaInstall)
```

## Major layers & responsibilities

| Layer | Responsibility | Key files |
|---|---|---|
| **Server render** | Next.js statically/server-renders the HTML; generates the manifest; serves SW headers | `app/layout.tsx`, `app/page.tsx`, `app/manifest.ts`, `next.config.ts` |
| **Data** | Holds the 10 reading items as typed constants; defines the `ReadingItem` shape | `lib/cards.ts`, `lib/types.ts` |
| **State/behavior** | Manages accordion state, scroll progress, back-to-top visibility, PWA install capability | `hooks/*.ts` |
| **Presentation** | Renders UI: hero, cards, progress bar, buttons, SW registrar | `components/*.tsx` |
| **PWA/offline (client only)** | Registers SW; precaches shell; intercepts network requests; provides install affordance | `public/sw.js`, `public/offline.html`, `components/ServiceWorkerRegistrar.tsx`, `components/InstallButton.tsx`, `hooks/usePwaInstall.ts` |

## Data flow (primary user journey: reading a card)

1. User opens the site → Next.js server renders `app/page.tsx` → HTML sent to browser.
2. `ReadingList.tsx` reads the static `readingItems` array from `lib/cards.ts`.
3. `ReadingList` renders one `ReadingCard` per item; whether a card is expanded is driven by the `expanded` prop from the `useCardStates` hook.
4. Clicking a card header calls `toggleCard(id)` → `useCardStates` updates `activeCard` → `ReadingList` re-renders with the new expanded card → the previous card collapses (single-open accordion).
5. State is persisted to `localStorage` under `bedtime_card_states`.
6. On next visit, the saved card is restored after hydration.

# 6. Entry Points & Execution Flow

## Entry points

| Entry point | File | Type | Purpose |
|---|---|---|---|
| **Root layout** | `app/layout.tsx` | Server Component | Wraps all pages: `<html lang="bn">`, metadata, Google Fonts preconnect/link, theme color, and mounts the `ServiceWorkerRegistrar` |
| **Home page** | `app/page.tsx` | Server Component | Composes the entire UI: ProgressBar, main container (Hero, InstallButton, ReadingList), ScrollToTopButton |
| **Manifest route** | `app/manifest.ts` | Route handler | Generated by Next.js at `/manifest.webmanifest` |
| **Service Worker** | `public/sw.js` | Client worker script | Registered by `ServiceWorkerRegistrar`; handles offline/network interception |
| **Offline fallback** | `public/offline.html` | Static HTML | Served by the SW when offline and no cached page exists |

## Execution flow (first visit)

1. User requests `https://<host>/`.
2. **Next.js server** runs `app/layout.tsx` (root layout) which sets `<html lang="bn" dir="ltr">`, injects the Google Fonts stylesheet links, and places `<ServiceWorkerRegistrar />` (renders `null` on the server).
3. **Next.js server** runs `app/page.tsx`, which server-renders `ProgressBar` (0% width), `HeroSection`, `InstallButton` (renders `null` initially), `ReadingList` (all cards collapsed — matching `useCardStates` initial state of `null`), and `ScrollToTopButton` (with `hidden` class).
4. HTML + statically-linked CSS/JS are sent to the browser.
5. **Browser hydrates** the React tree. Client components run their `useEffect`s:
   - `ServiceWorkerRegistrar` registers `/sw.js` only if `NODE_ENV === "production"`, after `window.load`.
   - `useCardStates` reads `localStorage["bedtime_card_states"]`, normalizes legacy data, and expands the previously opened card.
   - `useScrollProgress` computes initial progress and attaches scroll/resize listeners.
   - `useScrollToTop` computes initial scroll position and attaches a scroll listener.
   - `usePwaInstall` captures `beforeinstallprompt` (Chromium) and detects standalone mode.
6. The **Service Worker** installs (in production), precaching the app shell, then activates and takes control.
7. On subsequent navigations/requests, the SW intercepts fetches using its caching strategies (network-first for navigations, cache-first for hashed assets, stale-while-revalidate for fonts).

## User interaction flow: opening a card

1. User clicks a card header (or presses Enter/Space when focused).
2. `ReadingCard`'s `onClick`/`onKeyDown` fires → calls `onToggle` → `ReadingList.toggleCard(item.id)`.
3. `useCardStates.toggleCard` sets the new `activeCard` (closing any previously open card) and persists to `localStorage`.
4. React re-renders: the clicked card no longer has the `collapsed` class (its body animates open via CSS `max-height`); the previous card gained the `collapsed` class (animates closed).
5. The `aria-expanded` attribute updates accordingly.

# 9. Frontend Analysis

## Overview

A single-page, SSR'd React app with 7 components and 4 hooks. The entire UI is the reading list of 10 collapsible cards, wrapped in a styled hero.

## Pages / Routes

| Route | Component | Notes |
|---|---|---|
| `/` | `app/page.tsx` | The only page. Server Component that composes all UI |
| `/manifest.webmanifest` | `app/manifest.ts` | Generated manifest (not a UI page) |

There are **no other routes** — no dynamic routes, no API routes, no error pages (no `error.tsx`, `not-found.tsx`, or `loading.tsx`).

## Components

### HeroSection.tsx (Server Component)
- **What it shows:** the app logo (`/favicon.png` via `next/image` with `priority`), the Bengali title, the English subtitle, and an italic description tagline.
- **Styling:** `.top-title-section`, `.moon-symbol`, `.hero-logo`, `.title-bn`, `.title-en`, `.subtitle` classes in `globals.css`.

### ReadingList.tsx (Client Component)
- **Responsibility:** renders all 10 `ReadingCard`s from `readingItems`; owns the single-open accordion state via `useCardStates`.
- **Key line:** `const { activeCard, toggleCard } = useCardStates();` — passes `expanded={activeCard === item.id}` and `onToggle={() => toggleCard(item.id)}` to each card.

### ReadingCard.tsx (Client Component, presentational)
- **Props:** `item: ReadingItem`, `expanded: boolean`, `onToggle: () => void`.
- **Behavior:**
  - Clicking the header toggles; Enter/Space keys toggle (with `preventDefault()` on Space to prevent page scroll).
  - `role="button"`, `tabIndex={0}`, `aria-expanded`, `aria-controls` for accessibility.
  - Renders Arabic text (`dir="rtl"`), Bengali pronunciation, and Bengali meaning. Line breaks in content (`\n`) are converted to `<br />`.
  - The `collapsed` class drives the CSS open/close animation.
- **Dependencies:** `lucide-react` (ChevronDown icon), `lib/types.ts` (ReadingItem type).

### ProgressBar.tsx (Client Component)
- Shows a fixed 5px reading progress bar at the top.
- Width is driven by `useScrollProgress()` (`style={{ width: `${progress}%` }}`).
- Styled via `#progress-container` / `#progress-bar` with an animated shimmer gradient.

### ScrollToTopButton.tsx (Client Component)
- Floating circular button, bottom-right.
- Visible after scrolling past 350px (handled by `useScrollToTop`), smooth-scrolls to top.
- Uses `ArrowUp` icon; accessible `aria-label="উপরে যান"` and `title="উপরে যান"`.

### InstallButton.tsx (Client Component)
- Renders **nothing** (`return null`) unless `usePwaInstall().canInstall` is true.
- When visible: a pill-shaped "অ্যাপ ইনস্টল করুন" button with a `Download` icon; clicking calls `promptInstall()` which triggers the browser's native install dialog.
- **Note:** `canInstall` is only true when a `beforeinstallprompt` event is captured (Chromium) AND the app is not running standalone. On iOS/Safari it never renders — that's intentional (iOS doesn't support programmatic install).

### ServiceWorkerRegistrar.tsx (Client Component)
- Renders `null` but has a `useEffect` that registers `/sw.js` with scope `/`.
- **Production-only** (`process.env.NODE_ENV !== "production"` guard) so dev servers don't cache changing assets.
- Waits for `window.load` before registering so it doesn't compete with initial render/bandwidth.
- Registration failures are silently swallowed (the app still works online).

## Hooks

| Hook | Purpose | Notable implementation details |
|---|---|---|
| **useCardStates** | Single-open accordion state + localStorage persistence | Hydration-safe (initial `null`); defensive parsing with `pickActiveFromStored`; normalizes legacy multi-open map data to the first expanded card; persists as `{ [activeId]: true }` or `{}` |

# 17. Important User / Request Flows

## Flow 1: First visit (online, production)

```
GET / →
  Next.js SSR: layout.tsx → page.tsx →
  HTML sent →
  Browser hydrates →
  useEffect: SW registrar registers /sw.js (after window.load) →
  SW installs: precaches offline.html, /, manifest, icons →
  SW activates: cleans old caches, enables navigationPreload, claims clients →
  DOM rendered: progress bar (0%), hero, collapsed cards, hidden scroll-top button
```

## Flow 2: Reading a card

```
User clicks card header →
  ReadingCard.onToggle → ReadingList.toggleCard(item.id) →
  useCardStates: setActiveCard (creates/clears) + persist to localStorage →
  Re-render: clicked card gets .reading-card (no .collapsed) → card-body animates open →
  aria-expanded="true" →
  User reads Arabic (RTL) → transliteration → meaning
```

## Flow 3: Refresh while a card is open

```
Page reload →
  Server renders all cards collapsed (hydration-safe) →
  Browser hydrates →
  useCardStates useEffect: reads localStorage["bedtime_card_states"] →
  pickActiveFromStored parses & validates →
  setActiveCard(savedId) → saved card re-expands after mount →
  (Legacy multi-open data normalized to first open card)
```

## Flow 4: PWA install (Chromium desktop/Android)

```
Chrome determines app is installable (manifest + SW present) →
  fires beforeinstallprompt →
  usePwaInstall: e.preventDefault() (suppresses mini-infobar), stores deferredPrompt →
  canInstall = true (if not standalone) →
  InstallButton renders "অ্যাপ ইনস্টল করুন" →
  User clicks → promptInstall() → deferredPrompt.prompt() → native dialog →
  User accepts → appinstalled event fires → deferredPrompt cleared, isStandalone=true →
  InstallButton disappears
```

## Flow 5: Offline navigation

```
User offline, navigates to a page never visited →
  SW fetch handler: request.mode === "navigate" → handleNavigation →
  Try network (fails offline) → catch block →
  Look for exact cached page → fall back to cached "/" → fall back to cached "/offline.html" →
  Serve offline.html (or cached content)
```

## Flow 6: Font loading offline

```
First online visit:
  Font stylesheet + font files fetched → SW staleWhileRevalidate caches them (opaque-safe)
Offline visit:
  SW serves fonts from cache immediately while attempting revalidation (which fails silently → cache used)
```

- No React error boundary component in the tree

- No structured logging
- No API error handling (no API)

## Failure pathway (example: localStorage unavailable in private mode)

```
User opens app in a browser with localStorage blocked →
```

# 28. Final Complete Project Summary

## 1. What is this project?

A single-page, installable **Progressive Web App** called **"ঘুমানোর পূর্বের সূরা ও দোয়া" (Bedtime Surahs & Duas)**. It is a lightweight digital reader presenting 10 authentic Islamic Surahs and Duas for nightly recitation before sleep.

## 2. What problem does it solve?

It provides a clean, distraction-free, **mobile-first, offline-capable** way to recite bedtime Adhkar (Surahs and Duas). Users no longer need an internet connection after the first visit, and the app can be installed to the home screen like a native app — replacing the need to keep a browser tab or paper book handy.

## 3. Who is it for?

Bengali-speaking Muslims who want a curated, personal collection of specific bedtime Surahs and Duas in Arabic with Bengali transliteration (pronunciation help) and Bengali meaning. The maintainer describes it as "একটি ব্যক্তিগত সংগ্রহ" (a personal collection).

## 4. How does it work?

- Next.js statically/server-renders a single page showing 10 collapsible cards (one per Surah/Dua).
- Each card shows Arabic (RTL), then Bengali pronunciation (উচ্চারণ), then Bengali meaning (অর্থ).
- Cards form a **single-open accordion** — at most one expanded at a time — with the state persisted to `localStorage` and restored on revisit.
- A **hand-written Service Worker** (registered in production only) precaches the app shell. It serves navigations network-first (fresh when online, cached when offline), build assets cache-first (immutable hashed files), and Google Fonts stale-while-revalidate.
- The app can be **installed** via a self-hiding button that triggers Chromium's native install dialog.
- When offline and no cached page matches, a styled `offline.html` fallback page displays a friendly Bengali message.

## 5. What technologies does it use?

- **Next.js 15** (App Router) — SSR, static generation, manifest route, custom headers
- **React 19** + **TypeScript** (strict)
- **Tailwind CSS 4** + extensive custom CSS design tokens (`@theme`)
- **lucide-react** — icons
- **Hand-written Service Worker** (plain JS, no Workbox/next-pwa)
- **Browser localStorage** — accordion state persistence
- **Google Fonts** — Amiri, Noto Naskh Arabic, Noto Serif Bengali, Hind Siliguri
- **npm** — package manager

## 6. What are its major components?

- **Hero section** — branding/logo and titles
- **Reading list** — 10 collapsible cards (the core content)
- **Reading progress bar** — scroll indicator at top
- **Back-to-top button** — floating navigation aid
- **Install button** — self-hiding PWA install affordance
- **Service Worker** — offline/caching engine
- **Offline fallback page** — graceful offline message
- **Web App Manifest** — installable app metadata + icons

## 7. How does data flow through it?

```
Static TypeScript data (lib/cards.ts)
  → imported by ReadingList (serialized server-side into HTML)
  → rendered by ReadingCard (Arabic, transliteration, meaning)
  → user interaction toggles state in useCardStates
  → state persisted to localStorage
  → restored on subsequent visits (hydration-safe)
  → Service Worker caches the page/assets for offline use
```

## 8. What are its most important features?

1. 10 verified Surahs/Duas with Arabic + Bengali transliteration + meaning
2. Single-open accordion with localStorage persistence (hydration-safe, legacy-data-compatible)
3. Full **offline support** (precache + network-first navigations + offline fallback page)
4. **Installable PWA** (manifest, icons, self-hiding install button, standalone detection)
5. **Accessibility** (keyboard, ARIA, reduced-motion, RTL/LTR handling)
6. **Responsive design** (3 breakpoints)
7. **Reading experience UX** (progress bar, back-to-top, smooth scroll, artisan light theme)

## 9. What are its major dependencies?

Only **4 runtime** and **6 dev** dependencies — extraordinarily lean:
- Runtime: `next`, `react`, `react-dom`, `lucide-react`
- Dev: `tailwindcss`, `@tailwindcss/postcss`, `typescript`, `@types/node`, `@types/react`, `@types/react-dom`

## 10. What are its biggest technical risks?

1. **No automated tests** — the accordion persistence and SW caching logic are complex and unprotected against regressions.
2. **Manual SW cache versioning** — forgetting to bump `CACHE_VERSION` after changing the precached shell means stale offline assets; mitigated but not eliminated.
3. **Google Fonts dependency** — render-blocking third-party fonts; a `next/font` migration is the planned fix (noted in code).
4. **No lint/format enforcement** — drift risk as the project grows.
5. **No license** — reuse terms are undefined.

## 11. What are the most important files?

See **Section 18 — Important File Map** above for the full ranked list; the top five are `lib/cards.ts` (data), `components/ReadingList.tsx` + `hooks/useCardStates.ts` (core logic), `public/sw.js` (offline engine), and `next.config.ts` (SW headers — the one config that matters).

## 12. What should a new developer understand first?

1. This is a **static, content-only app** — there is no backend, database, auth, or API to learn.
2. The **data model** (`ReadingItem` in `lib/types.ts`, data in `lib/cards.ts`) drives everything the UI renders.
3. The **state pattern** is simple: React `useState` + `localStorage` + custom hooks — no state library.
4. The **PWA layer is additive**: `ServiceWorkerRegistrar` mounts in the root layout, registers `sw.js` in production only, and `public/sw.js` implements the caching strategies.
5. The **README.md is excellent and authoritative** — read it before touching any code, especially for PWA cache-roll procedures.
6. Everything is **TypeScript-strict** and heavily commented, so the code is unusually self-documenting.
